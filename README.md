# BYTE BACK 자료실 · 12단계 저장점

## 검사 기준과 재현 안내

검사 기준 저장점은 `f488bd8c10396ae29395c07b14ebc0b8f9c2b749` (「11단계 기기 승인 서버 연결」)입니다.
이는 현재 작업의 기준 커밋이며, 그 커밋 전체나 운영 기능의 검증 완료를 뜻하지 않습니다.
12단계 작전실·41종 확인 표·이 안내는 「12단계 저장점」커밋에 포함합니다. 기준 커밋만 체크아웃하면
12단계 파일은 없습니다. 이 저장점의 실제 커밋 번호와 배포 응답을 대조한 뒤 재현합니다.
설정 step은 12이며 배포 주소·발급자·원본 API·restoreRoute·자료 허용 경로 15개·judgeIssuer를 보존했습니다.
작전실 API는 앱 전용이며 판정기의 허용 구역을 넓히지 않습니다. RULE_IDS는 구현된 세 규칙만 유지합니다.

이번 작업에서 실행한 검사는 작전실/승인 거부·화면의 모의 시험, 기존 PWA·API 권한 모의 시험과
`npm run build -- --local`입니다. 41종 실제 요청·운영 엔진 재현·물리 기기 검증·회수 집행·실제 복구는
미실행입니다. 아래 명령과 배포 순서는 실행 안내이며 새 설치·새 배포 완료 기록이 아닙니다.
아래의 과거 단계별 절은 해당 저장점 당시의 기록입니다. 현재 상태는 이 절과 11단계 서버 승인 설명을 우선합니다.

## 학생 코드와 제공 엔진의 출처

이 프로젝트는 **ALEPH SDP 엔진 사용**을 전제로 하는 학생 방어전 코드입니다.
제공 엔진은 학생이 제작한 엔진으로 표시하지 않습니다. 계약 문서가 참조하는 제공 측 파일은
`student-kit/sdp-core/decision-contract.mjs`이며, 그 엔진 구현·설치 프로그램은 이 저장소에 없습니다.
운영 엔진의 설치·실행·중지·복구는 운영 측 공식 배포본과 안내를 사용해야 합니다. 엔진 주소·실행 명령·
규칙 등록 API를 추정하지 않습니다. 현재 서버 기기 승인은 실제 엔진 연결을 대신하지 않는 시험 모델입니다.

## 설치와 실행 순서

1. Node.js 22 이상·npm·Git을 준비합니다. 기존 폴더를 덮어쓰지 않고 별도 폴더에 저장소를 받습니다.
   GitHub 저장소: https://github.com/NohHyoungJ/choi-bujang-secret-vault_2
   현재 기준을 재현할 때는 그 새 폴더에서 다음 순서를 사용합니다.

   ```powershell
   git clone https://github.com/NohHyoungJ/choi-bujang-secret-vault_2.git vault-reproduction
   cd vault-reproduction
   git checkout --detach f488bd8c10396ae29395c07b14ebc0b8f9c2b749
   npm ci
   ```

   위 기준에는 12단계 미커밋 파일이 없습니다. 12단계 재현은 해당 작업이 저장된 뒤 그 커밋으로
   별도 체크아웃합니다. 현재 작업 폴더에서 과거 커밋으로 이동하거나 파일을 덮어쓰지 않습니다.
2. 학생 판정기: `npm run decider:test` → `npm run fixture:7` 순서로 가상 정상·금지 요청을 확인합니다.
   정상 허용 구역의 등록 요청은 allow, 미등록은 deny, 복합 의심은 step_up이어야 합니다.
   실제 운영 요청 적용은 제공 엔진 설치·계약 연결을 운영 측에서 확인한 뒤 별도로 측정합니다.
3. 탐지: `npm run detect:test`로 제공 사건 계약을 확인하고, 필요하면
   `node scripts/detect-fixture-test.mjs`로 로컬 확장을 따로 실행합니다. 정상은 observe,
   동일 주체의 10분 내 GET 121건은 propose_revocation이어야 합니다. 제안 성공은 회수 집행이 아닙니다.
   XDR 가상 경보는 `npm run xdr:run -- brute-force`와 `npm run xdr:run -- web-injection`으로 각각 실행합니다.
   result.json은 가상 분류 결과이며 respond.mjs의 운영 어댑터 미연결 상태를 실제 차단으로 보고하지 않습니다.
4. 정적 빌드 확인: `npm run build -- --local`. 이 명령은 public/data.json을 갱신하며
   서버 API·실제 로그인·DB 연결을 실행하지 않습니다. 별도의 npm start/dev 스크립트는 없습니다.
5. 자료실 실행은 Vercel의 별도 시험 프로젝트에 검토한 GitHub 커밋을 연결하는 방식입니다.
   vercel.json의 빌드 명령은 `npm run build`, 공개 폴더는 public입니다. 일반 빌드는 Vercel의
   실제 저장소·커밋·배포 주소 정보가 필요하므로 로컬에서 가짜 배포 변수를 만들어 우회하지 않습니다.
   새 주소를 쓸 경우 publicAppUrl과 공식 로그인 리디렉션·출처 설정을 먼저 검토하고
   judgeIssuer는 변경하지 않습니다. 제공 엔진 연결을 배포 완료만으로 가정하지 않습니다.
6. 서버 환경 변수는 이름과 용도만 전달합니다. SUPABASE_URL은 공식 프로젝트 주소,
   SUPABASE_SECRET_KEY는 서버 Auth/DB 접근용입니다. 실제 값은 소유자가 Vercel 공식
   Settings → Environment Variables의 비밀 입력란에 직접 설정합니다. 복원 기능에 필요한
   NOTE_RESTORE_BACKUP_JSON·NOTE_RESTORE_BACKUP_SHA256·NOTE_RESTORE_TEST_SUBJECT_ID도
   같은 방식으로 관리하며, 사본·계정 ID·값을 안내서에 채워 넣지 않습니다.
   DB 스키마는 supabase/migrations 및 docs/device-approval-schema.sql을 검토해 별도 시험 DB에 준비합니다.
   기존 DB에 재적용했다고 가정하거나 기존 권한·학습 자료를 덮어쓰지 않습니다.
7. 브라우저에서 검토한 배포 주소 → 로그인 → 기기 승인 요청 → 관리자의 해당 시험 접속 승인 →
   승인 결과 다시 확인 순으로 진행합니다. 승인된 본인 자료는 허용되고 미승인은 403,
   승인된 상대 자료는 404, 무로그인은 401이어야 합니다. 세부 승인 절차는 docs/DEVICE_APPROVAL.md에 있습니다.
   12단계 배포에서는 작전실 요약 새로고침 → 응답 recordId와 operations_summary 서버 기록 대조 →
   docs/VERIFICATION_1_11.md의 실측 순서로 진행합니다. 요약 조회 성공을 41종 시험 통과로 계산하지 않습니다.

## 중지와 다시 시작

- 로컬 가상 시험·빌드 명령은 완료하면 종료합니다. 실행 중인 자신의 터미널 작업만 Ctrl+C로 중지합니다.
  node 프로세스 전체를 종료하거나 다른 작업을 중지하지 않습니다. 이 저장소에는 상시 판정·탐지 데몬이 없습니다.
- 브라우저는 로그아웃 후 창을 닫습니다. 앱 제거는 해당 브라우저의 앱 관리 메뉴에서 합니다.
  앱 제거·창 닫기는 서버 접근 중지나 물리 기기 권한 회수를 의미하지 않습니다.
- 시험 접속 접근 중지는 관리자가 해당 승인 요청 한 건을 철회하는 절차를 사용합니다.
  다음 서버 확인부터 거부되는지 실측합니다. Supabase 전체 프로젝트·메모 테이블·다른 접속은 삭제하지 않습니다.
- 배포 서비스를 중지해야 하면 소유자가 Vercel의 해당 시험 프로젝트 접근/배포 운영 설정에서 처리합니다.
  실제 ALEPH SDP 엔진·수집기 중지는 운영 담당자의 공식 절차로 별도 수행합니다.
  로컬 판정 함수의 호출을 중단했다고 기존 엔진 정책·이미 설치한 거부 규칙이 해제되지는 않습니다.
- 다시 시작은 서버 상태 → 동일 배포 커밋 → 로그인·현재 접속 승인 → 정상/금지 재확인 순서입니다.

## 복구와 재검증

1. 오류 시 쓰기 시험을 멈추고 커밋·배포·안전한 오류 코드만 기록합니다. git status와 git diff로
   이번 변경과 다른 작업을 구분합니다. git reset --hard나 DB 전체 초기화를 사용하지 않습니다.
2. 앱 코드 복구는 Vercel에서 이전에 검증된 배포를 식별한 뒤 공식 되돌리기 절차를 사용합니다.
   로컬 기준 커밋이나 가장 최근 커밋을 자동으로 안전 버전으로 간주하지 않습니다.
   배포 되돌리기는 DB 자료·권한·외부 엔진 정책 복구를 대신하지 않습니다.
3. 시험 정책은 docs/RESTORE_PREVIEW.md에 따라 검증된 사본·신뢰한 검증 기록·외부 확인 해시를 준비한 후
   `npm run restore:preview -- --backup <사본파일> --current <현재시험정책> --verification <검증기록> --trusted-verification-sha256 <외부확인기준값>`
   으로 차이를 확인합니다. 입력이 없거나 검증이 실패하면 변경 없이 중단해야 합니다.
   적용은 문서의 restore:test-policy 미리보기와 확인 코드 절차로 policies/test 안의 선택 서비스에만 합니다.
   제공 엔진의 실제 정책 복구는 운영 측 공식 절차가 필요하며 이 로컬 JSON 교체로 대체하지 않습니다.
4. 지정한 B 가상 메모 복구는 기존 POST /api/restore-note를 사용하며, 로그인·시험 승인·서버 사본 검증이
   준비된 경우에만 요청합니다. 응답의 세 검증값 일치와 타 자료 보존을 확인합니다. 사본이 없으면 중단합니다.
   메모 본문·소유자 값·비밀 설정은 복구 로그·표·화면 요약에 기록하지 않습니다.
5. 복구 뒤 README의 1〜9단계 순서와 docs/VERIFICATION_1_11.md를 따라 정상 허용과 금지 거부를 각각
   실제 응답·요청 ID·시각으로 남깁니다. 운영 회수·복구 버전은 실제 기록이 없으면 미실행으로 유지합니다.

## 비밀값 없는 전달 범위

격리 환경의 bundle 자기 점검은 공개 HTTPS의 GET·HEAD만 전송합니다. POST·PUT·DELETE 등
쓰기 점검은 요청하지 않고 observed를 `not_run`으로 남깁니다. AbortSignal.timeout에 의존하지 않습니다.
`node --test test/bundle-isolation.test.mjs`는 이 제한을 모의 시험하며 실제 심판 실행과 구분합니다.

포장 대상은 검토한 학생 소스·공개 설정·잠금 파일·문서·안전한 가상 시험 코드입니다.
비밀번호·토큰·개인키·서버 키·실명·메모 본문·복구 사본·환경 설정 파일·원문 HAR/로그는 전달하지 않습니다.
node_modules·.vercel·DB 연결 임시 파일도 재배포 포장 대상에서 제외합니다. .gitignore만 믿지 말고
실제 포장 파일 목록과 내용을 검사합니다. 제공 엔진 바이너리·운영 설정을 이 학생 코드의 제작물로 묶지 않습니다.
bundle-notes.json과 artifacts/submission.json은 Git에 넣지 않습니다. 공식 제출 JSON은 npm run bundle로
생성한 뒤 민감정보·미실행 항목을 확인하여 지정 제출 경로에서만 취급하며, 일반 재배포 포장에 섞지 않습니다.
이번 README 작성에서는 포장·커밋·배포·복구 명령을 실행하지 않았습니다.

로그인 자료실과 메모 CRUD에 API 소유자 검사·RLS·원본 DB 직접 권한 회수를 추가했습니다. 6~7단계의 기기·가상 추가 확인 규칙에 이어, 8단계에서는 자료 구역 규칙과 API의 저장된 권한 재확인을 구현했습니다.

## 현재 기능

- Supabase 공식 SDK 이메일·비밀번호 로그인·로그아웃은 서버의 /api/session에서 처리하고 실패 이유를 화면에 표시합니다. 브라우저 코드에는 Supabase 공개 키·SDK·JWT가 없으며 HttpOnly·Secure·SameSite=Strict 쿠키로 서버에 인증합니다.
- 자료 API는 기존 `src/verify-login.mjs`로 토큰을 검증하며 브라우저의 userId·role을 신뢰하지 않습니다.
- 목록 GET은 검증된 사용자의 메모 배열을 반환합니다. 새 메모의 owner_id는 서버가 확인한 사용자 ID입니다.
- POST /api/learning-notes: {id?,title,body}, id는 UUID이며 생략하면 서버가 생성해 {id}를 반환합니다.
- GET·PUT·DELETE /api/learning-notes/:id. 단건 GET은 {id,title,body}, 삭제 뒤 GET은 404입니다.
- 개별 조회·수정·삭제는 검증된 사용자 ID와 owner_id를 같은 DB 요청에서 비교합니다. 상대 메모는 404이며, 수정 본문에 owner_id가 있으면 400으로 거부합니다. 수정 전후 소유자는 본인으로 유지됩니다.
- 학습 DB의 RLS 정책은 authenticated의 SELECT·DELETE에 USING, INSERT에 WITH CHECK, UPDATE에 둘 다 auth.uid() = owner_id를 적용합니다. 4단계에서는 authenticated CRUD를 허용했으나 5단계에서는 PUBLIC·anon·authenticated의 메모 테이블 직접 권한을 회수했습니다. RLS 정책은 보존했습니다.
- 기존 가상 메모 4개와 숫자 기본키를 보존하고, API용 UUID note_id 컬럼을 추가했습니다. 본인 소유가 아닌 기존 메모는 본인 목록에 나오지 않습니다.

## 10단계 저장점 구현과 검증 범위

시험 정책의 검증된 안전 사본을 미리보고 확인 코드로 선택 서비스만 복원하는 로컬 절차, 비공개 B 가상 메모 한 건 복원 POST 경로, 복구 뒤 1~9단계 재검사 순서를 추가했습니다. 다른 서비스와 기존 감사 이력을 보존하며 실제 운영 정책은 적용 대상이 아닙니다. 사본·검증·확인 코드가 없거나 상태가 달라지면 중단합니다.

aleph.config.json은 step 10, restoreRoute `/api/restore-note`이며 기존 배포 주소·로그인 발급자·허용 경로 15개·원본 API를 보존했습니다. judgeIssuer와 접속 판정 RULE_IDS 세 개는 유지합니다. 실제 안전 정책 사본·검증 기록과 B 비공개 사본·서버 설정이 없어 실제 복구와 복구 뒤 재검사는 미실행입니다. 합성·모의 시험 통과와 배포 API의 무인증 거부 확인을 실제 복구 완료로 보고하지 않습니다.

재실행: `node --test test/restore-preview.test.mjs test/restore-test-policy.test.mjs test/restore-note.test.mjs test/api-resource-access.test.mjs`. 화면 조작 없이 터미널에서 합성 정책 범위·감사 보존, 합성 B 메모의 ID·소유자·해시 일치, B의 A 접근 거부 뒤 A 정상 조회 유지를 확인합니다. 실제 사본 없는 복원 명령은 중단돼야 합니다. 실제 확인 화면·명령·기대 결과는 아래 절차와 `docs/RESTORE_PREVIEW.md`에 있습니다.

## 10단계 지정 메모 한 건 복원 API

서비스 ID는 `notes_restore`, 경로는 **POST `/api/restore-note`**이며 aleph.config.json의 restoreRoute에 기록했습니다. 요청 본문은 `{id}` 한 항목만 받습니다. 판정기의 자료 허용 경로 목록을 넓히지 않으며, 로그인 검증과 쿠키 요청의 출처 검사 및 지정한 B 시험 계정 제한을 API에서 적용합니다. 서버가 검증하는 Bearer 요청도 같은 B 계정 제한을 적용합니다. 메모 소유자·내용·역할을 요청 본문에서 받지 않습니다.

비공개 가상 사본은 서버의 비밀 설정 `NOTE_RESTORE_BACKUP_JSON`에서만 읽고 `NOTE_RESTORE_BACKUP_SHA256`과 원문 SHA-256을 대조합니다. 사본 형식은 schema `aleph.synthetic-note-backup.v1`, environment `test`, notes 배열이며 각 항목은 id·ownerId·title·body·contentSha256입니다. 내용 해시는 UTF-8 `JSON.stringify({title, body})`의 SHA-256입니다. 사본에 지정 ID가 한 건만 있어야 하고, 소유자는 검증된 B와 같으며 내용 해시도 같아야 합니다. 사본·외부 확인 해시·B 설정이 없으면 중단합니다.

Vercel 공식 Settings → Environment Variables의 서버 비밀 입력란에서 위 두 값과 `NOTE_RESTORE_TEST_SUBJECT_ID`(B 시험 계정의 사용자 ID)를 학생이 직접 설정해야 합니다. 값 자체를 채팅·Git·공개 JSON에 넣지 않습니다. 사본을 새로 자체 승인하거나 실제 사용자 메모로 시험하지 않습니다. 이 환경에는 실제 비공개 사본과 B 설정이 없어 실제 배포 복원은 미실행입니다.

복원은 learning_notes의 해당 note_id 한 행만 삽입하거나 같은 owner_id 조건으로 제목·내용만 수정합니다. 다른 소유자와 ID가 충돌하면 거부하며 upsert로 덮어쓰지 않습니다. 기존 숫자 기본키·생성 시각·다른 메모·감사 이력은 변경하지 않습니다. 성공 응답은 restored와 ID·소유자·내용 해시 일치 여부만 반환하며 본문·소유자 값·토큰은 출력하지 않습니다. 완료 또는 고정 오류 코드만 서버 로그에 추가합니다.

확인 명령: `node --test test/restore-note.test.mjs`. 합성 B 메모 한 건의 삽입·복원에서 ID·소유자·내용 해시 일치와 다른 메모·기존 감사 보존을 모의 시험합니다. A의 복원 요청·위조 본문·해시 불일치·다른 소유자 충돌은 쓰기 전에 거부해야 합니다. 실제 계정·토큰·서명 키·DB는 사용하지 않습니다.

배포와 비밀 설정이 준비된 뒤 **B 로그인 → 개발자 도구 Console**에서 실행합니다:
`fetch('/api/restore-note', {method: 'POST', credentials: 'same-origin', headers: {'Content-Type': 'application/json'}, body: JSON.stringify({id: '복원할 B 가상 메모 UUID'})}).then(async r => console.log(r.status, await r.json()))`.
정상은 200과 verification의 세 값이 모두 true여야 합니다. A는 403, 사본 내용 해시 불일치는 422, 소유자 충돌은 409, 사본 없이는 503이어야 합니다. 실제 복원·심판 결과로 모의 시험을 보고하지 않습니다.

## 10단계 복구 뒤 1~9단계 재검사 순서

**현재 상태: 실제 정책 사본·검증 기록과 비공개 B 메모 사본·서버 설정이 없어 실제 복구 및 복구 뒤 재검사는 모두 미실행입니다.** 아래는 실행할 순서와 기대 결과이며 완료 기록이 아닙니다. 앞서 통과한 합성·모의 시험을 복구 후 실제 통과로 옮겨 적지 않습니다. 이 순서를 처음 문서화한 요청에서는 시험을 실행하지 않았습니다. 10단계 저장점에서는 아래 합성·모의 검사만 다시 실행했으며 실제 복구 후 시험은 아닙니다.

### 0. 복구 대상과 적용 범위 확인

1. 시험 정책 미리보기에서 서비스·현재 버전·안전 사본 버전·추가/제거 항목·확인 코드를 확인합니다. 사본 없음·검증 실패·침해 이후 검증·예상 밖 변경이면 중단합니다. 절차는 `docs/RESTORE_PREVIEW.md`에 있습니다.
2. 확인 코드로 선택한 시험 서비스만 복원합니다. 다른 서비스 정책과 기존 감사 이력이 그대로이고 복원 감사 항목만 한 건 추가됐는지 비교합니다. 로컬 정책 JSON 복원은 실행 코드나 운영 엔진 정책의 복원을 의미하지 않습니다. 실제 요청에 그 정책이 적용되는 연결이 없으면 정책 적용 검증은 미실행으로 남깁니다.
3. B로 로그인해 POST `/api/restore-note`에 지정한 B 가상 메모 ID 한 건만 요청합니다. 200과 verification의 idMatches·ownerMatches·contentHashMatches가 모두 true인지 확인합니다. 다른 메모·기존 감사 기록을 비교하고, 비공개 사본은 덮어쓰지 않습니다. 실패하면 성공으로 기록하지 않고 재검사를 중단합니다.
4. 기존 자료실 화면에서 B의 복원 메모를 다시 조회합니다. ID·저장된 소유자·내용 해시가 사본과 같은지는 보호된 서버 확인과 위 검증값으로 확인하고, 자료 본문·소유자 값·토큰을 터미널이나 결과 기록에 출력하지 않습니다. A의 기존 자료 조회도 먼저 확인합니다. 실제 운영 정책의 수정·권한 부여로 실패를 우회하지 않습니다.

### 1. 이전 정상·금지 요청 재실행

### 2. 결과 기록과 종료 확인

각 실행 결과에는 단계·시험 종류(실제 HTTP/로컬 가상/대역/심판)·정상 또는 금지·기대 상태/사유·실제 상태/사유·실행 여부만 적습니다. 실행하지 않았으면 **미실행**, 응답을 확인하지 못했으면 **확인 불가**, 기대와 다르면 **실패**로 적습니다. 실제 소유자·메모 본문·토큰·실명은 기록하지 않습니다. 정책 버전·대상 건수·검증 일치 여부처럼 비밀값 없는 확인 결과만 남깁니다.

마지막에 B 복원 메모의 ID·소유자·해시 일치, A 정상 접근 유지, B의 A 접근 거부, 다른 메모·서비스·기존 감사 보존을 다시 확인합니다. 자료 복구 성공만으로 이전 차단 정책이 돌아왔다고 판정하지 않습니다. 실제 회수·복구 시간과 종합 통과는 심판이 확인합니다.

제출 점검 `npm run bundle`은 새 저장점 커밋과 배포 반영을 확인한 뒤 실행합니다. 생성 JSON의 미실행 항목과 기존 배포 대상 점검을 숨기지 않습니다. 실제 복구 뒤 결과가 없는 동안 기존 제출 JSON을 복구 완료 증거로 사용하지 않습니다. 이 작업 셸에는 npm이 없어 앞선 일부 스크립트는 제공 Node.js로 직접 실행했으며, 10단계 저장점에서 실행한 로컬 검사 기록은 아래와 같으며 실제 복구 후 재검사 표는 계속 미실행입니다.

## 11단계: 자료실 설치형 웹앱과 시험 접속 승인

앱 이름은 **BYTE BACK 자료실**입니다. 기존 주소에 manifest·192/512 아이콘·사용자 선택 설치와
공개 오프라인 안내를 제공합니다. 설치 표시와 기기 승인은 분리하며 설치 모듈은 승인 요소를 변경하지 않습니다.
서비스 워커는 공개 offline.html만 저장하고 메모·API·세션 응답·실패한 쓰기를 캐시하거나 재전송하지 않습니다.

### 서버 승인 연결

시험 사이트 안에 GET·POST **/api/device-approval**을 구현했습니다. 서버가 검증한 로그인 세션
하나를 가상 기기로 취급합니다. 실제 물리 기기 증명·운영 엔진 연동은 아닙니다.
버튼은 서버에 대기 요청을 만들며 승인 권한이 없습니다. 서버 전용 DB 테이블은 공개/일반 사용자에게
읽기·쓰기 권한이 없고, 앱 서버 역할에도 승인 상태 INSERT·UPDATE 권한을 주지 않았습니다.
관리자가 Supabase Table Editor에서 요청 번호를 확인하여 state와 approved_until을 설정합니다.
사이트에서 **승인 결과 다시 확인**을 누르면 GET으로 조회된 승인 상태에 따라 기존 자료실을 엽니다.

현재 로그인과 승인 결과를 요청마다 서버에서 대조합니다. 미승인 자료 요청은 403,
승인 조회 실패는 503이며 자료를 반환하지 않습니다. 승인 후에도 기존 소유자·강사 검사를 유지합니다.
HTML의 자료 영역은 hidden·inert로 닫혀 있고 승인 조회 오류·철회·만료·로그아웃·오프라인에서는
목록과 편집 내용을 지웁니다. 재연결·focus 때 서버 상태를 다시 조회합니다.
키·승인 토큰·추가 기기 쿠키는 만들지 않습니다. 기존 로그인은 HttpOnly 보안 쿠키로 유지하며
localStorage·sessionStorage·IndexedDB에 인증·승인 정보를 저장하지 않습니다.
새 로그인은 별도 승인이 필요하고, 외부 심판 토큰에 시험 승인을 자동 부여하지 않습니다.

상세 API·DB·관리자 승인 순서는 [시험 접속 승인 문서](docs/DEVICE_APPROVAL.md)에 있습니다.
**기존 저장점의 미연결 안내와 고정 false 잠금은 이번 서버 연결 구현으로 대체했습니다.**
실제 계정의 로그인·승인·철회·승인 후 CRUD와 브라우저 설치·오프라인 시험은 이번 수정 후 **미실행**입니다.
DB 테이블 생성과 권한 메타데이터 조회는 실행했습니다. 승인 행을 임의 생성하거나 실제 접속을 승인하지 않았습니다.

### 다시 확인하기

Node.js 22 이상과 npm이 있는 환경에서 npm install 후
`node --test test/pwa.test.mjs test/api-resource-access.test.mjs test/restore-note.test.mjs`를 실행합니다.
소유자·복원 모의 검사는 승인된 가상 상태에서 이전 기능을 확인하는 것으로 실제 승인 시험이 아닙니다.
이번 수정에서는 자동 시험을 실행하지 않았습니다.
실제 화면은 **로그인 → 기기 승인 요청 → 관리자 DB 승인 → 승인 결과 다시 확인** 순서입니다.
승인 전에는 목록·편집 화면과 자료 API 결과가 없어야 하고, 승인된 동일 접속은 본인 자료를 볼 수 있어야 합니다.
승인된 B의 A 메모 조회는 404, 미승인 접속은 403, 승인 조회 장애는 503이어야 합니다.
설치 또는 요청 버튼만 누른 상태에서 자료가 열리면 실패입니다.

### 단계·저장점 확인

설정 step은 11이며 실제 배포 주소·로그인 발급자·원본 API·허용 경로·judgeIssuer를 보존했습니다.
RULE_IDS는 device_registered·step_up_required·resource_scope 세 개를 유지합니다.
판정기의 엔진 요청 계약은 수정하지 않습니다. 별도 시험 승인 API를 판정기의 허용 자료 경로에 추가하지 않습니다.
기존 설치 확인은 빈 폴더의 package.json·잠금 파일로 npm 10.9.2 설치 성공이었으며,
판정 계약·구역 모의 검사 6개와 기존 판정 가상 요청 4개 통과는 앞선 저장점의 기록입니다.
이번 서버 연결 변경은 실제 로그인 세션을 가상 기기로 사용하는 시험 구현입니다.
실제 계정의 승인·철회 및 승인 후 화면 동작은 미실행이며, 커밋·푸시만으로 심사 통과를 뜻하지 않습니다.
제출 JSON과 bundle-notes.json은 Git에 포함하지 않습니다.

## 보너스 xdr-01 저장점

무차별 로그인 가상 경보를 다루는 xdr/brute-force 모듈을 추가했습니다. read-alerts.mjs는 다섯 필드만 추출하고 비밀값처럼 보이는 내용을 숨깁니다. patterns.json의 MITRE T1110·T1110.003 두 패턴을 decide.mjs 내부 상수로 복사했으며, 판정기는 외부 파일·패키지·네트워크 없이 계산합니다.

재실행: `npm run xdr:run -- brute-force`. 갱신된 result.json은 block 10건·alert 9건·record 9건입니다. 원본 설명상 정상 이벤트 bf-20~bf-28은 모두 record이며 오차단이 없었습니다. 이는 가상 경보 자기 점검이고 실제 차단이나 심판 판정이 아닙니다. 화면 조작은 없으며 터미널 결과 파일을 확인합니다.

respond.mjs는 만료 시각·경보 번호가 있는 후보를 deny-candidates.json에 기록하고 알림을 xdr/alerts.log에 한 줄씩 누적합니다. 정상·알림 대상, 만료 경보, 검증되지 않은 공격 기기는 규칙 등록에서 제외합니다. 실제 ZTNA 운영 어댑터와 검증된 공격 기기 연결은 없으므로 실제 규칙을 등록하지 않았습니다. 기존 src/decider.mjs와 가상 경보 원본은 보존했습니다.

본 저장점은 보너스 추가이며 aleph.config.json의 본 과정 단계는 5를 유지합니다. 실제 배포 주소·발급자·허용 경로 8개·원본 API 주소를 구현과 대조했고 judgeIssuer는 보존했습니다. RULE_IDS는 실제 기본 거부 규칙 starter.deny만 유지합니다.

## 보너스 xdr-02 저장점

웹 주입 가상 경보용 xdr/web-injection 모듈을 추가했습니다. read-alerts.mjs는 다섯 필드만 추출하고 비밀값처럼 보이는 값은 숨깁니다. patterns.json의 SQL 주입·스크립트 태그 삽입·반복 경로 탐색 패턴을 decide.mjs 맨 위 상수로 복사했습니다. decide(alert)는 외부 파일·패키지·통신 없이 판단 결과만 반환하며 0.85 이상 block, 0.5 이상 alert, 그 아래 record입니다.

재실행: `npm run xdr:run -- web-injection`. 명령 구분자 주입과 단발성 의심 신호를 보완한 result.json은 block 8건·alert 9건·record 9건입니다. 원본 설명상 정상 이벤트 wi-18~wi-26은 모두 record이며 정상 차단은 0건입니다. 같은 출발 주소에서 반복되는 명확한 주입은 차단 후보, 중간 수준의 단발성 의심 신호는 알림으로 구분합니다. 이는 학습용 경보의 로컬 자기 점검이며 실제 차단이나 심판 판정이 아닙니다. 화면 조작 없이 결과 파일을 확인합니다.

respond.mjs는 차단 후보에 5분 만료 시각과 근거 경보 번호를 붙이고, 검증된 공격 기기 및 등록된 이유 코드가 있을 때만 운영 연결 함수로 거부 규칙을 전달합니다. 알림은 xdr/alerts.log에 안전한 JSON 한 줄씩 기록합니다. 정상 이벤트·만료 경보·미확인 기기는 등록에서 제외하는 모의 연결 검증을 통과했습니다. 실제 운영 어댑터가 없어 실제 규칙 등록은 미실행이며, 이번 result 생성은 respond.mjs를 실행하지 않습니다. 기존 판정기와 경보 원본은 보존했습니다.

설정의 본 과정 단계 5·기존 배포 주소·발급자·허용 경로 8개·원본 API 주소와 RULE_IDS의 starter.deny를 유지했습니다. 이번 저장점에서 앱 배포나 DB 변경은 실행하지 않았습니다.

10단계 저장점 로컬 확인: 복원 미리보기·시험 정책 적용·합성 B 한 건 복원·API 권한·구역 검사 15개, 기존 접속 판정 4개, 제공 탐지 계약 6개를 제공 Node.js로 실행해 통과했습니다. 실제 복구·실제 B 계정·복구 뒤 1~9단계·심판 종합 검사는 미실행입니다.
